## `IJobParallelFor` — `Schedule(int arrayLength, int innerloopBatchCount, JobHandle dependsOn = default)`

| Call site                                                                              | Pattern                                                            |
|----------------------------------------------------------------------------------------|--------------------------------------------------------------------|
| `Packages/is.zori.volumetrics/Runtime/Authoring/VoxelTileFiller.cs:54`                | `job.Schedule(VoxelsPerTile, 64).Complete();` — **canonical positional** |
| `Packages/is.zori.heightfields/Heightfields/Runtime/Meshing/RegionMeshingService.cs:433` | `_decodeHandle = job.Schedule(p.SlotCount, 1);` — batch=1 (heterogeneous work) |

Project canon: pass `arrayLength` and `innerloopBatchCount` **positionally**. Named arguments are not used in the project — sidesteps the `batchSize` vs `innerloopBatchCount` vs `indicesPerJobCount` mistake described in [`scheduling-overloads.md`](scheduling-overloads.md).

The two call sites use different `innerloopBatchCount` strategies:
- `VoxelTileFiller.cs:54` uses `64`. With `VoxelsPerTile = 16³ = 4096` → 64 batches of 64. Per-voxel work is uniform (FBM + smin), so a moderate batch keeps overhead low without hurting load balance.
- `RegionMeshingService.cs:433` uses `1`. Per-slot work is heterogeneous (some regions are empty, some are dense meshes). Batch 1 means the work-stealer can fully load-balance across slots; the per-batch scheduling overhead is acceptable because per-slot work is the dominant cost.
