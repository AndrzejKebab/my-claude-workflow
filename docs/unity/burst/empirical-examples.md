## Default `[BurstCompile]` on a job struct

The dominant project pattern: bare `[BurstCompile]` (no properties) on the job struct, no attributes on helper static methods.

Project canon (`feedback_burst_entrypoints_only.md`): tag entry points only; helpers auto-compile. The `Hash3i` / `ValueNoise3` / `Fbm3` / `Smin` static methods inside `VoxelTileFillJob` (`VoxelTileFiller.cs:146–199`) carry no attribute — they Burst-compile because they are reached from a Burst entry point.

```csharp
partial struct SlimeLatticeSyncSystem : ISystem {

    [BurstCompile]                            // line 15

    [BurstCompile]                            // line 19

}
```

Cited at `Assets/_Project/Scripts/ECS/Systems/SlimeLatticeSyncSystem.cs:7,11,15,19`. The struct attribute marks the type as Burst-compilable; the per-method attributes are required because `ISystem` lifecycle methods aren't auto-Bursted from the struct attribute alone (they're called via interface dispatch from the systems group).

The pattern is "attribute on struct + attribute on every lifecycle method that should run native". See [`docs/unity/entities/system-types.md`](../entities/system-types.md) and [`docs/unity/entities/systems.md`](../entities/systems.md) for the full ISystem doc.

## Property-tweaked `[BurstCompile(...)]` (rare in this project)

A search across `Packages/is.zori.*` and `Assets/_Project/` for `BurstCompile(` (with parens) returns no project hits — i.e. **no project code uses** `FloatMode = ...`, `FloatPrecision = ...`, `OptimizeFor = ...`, etc. The project relies on Burst defaults (`FloatMode.Default`, `FloatPrecision.Standard`, `OptimizeFor.Default`).

If a future kernel needs determinism (e.g. multiplayer simulation) or fast-math (e.g. inner-loop signed-distance evaluation), it should adopt the property-tweaked form. See [`attributes.md`](attributes.md) for the FloatMode trade-offs.

## Static `[BurstCompile]` for shared utilities

A search for `[BurstCompile]` on plain static methods (not job structs) returns no project hits. The project does not currently expose Burst-direct-call utility functions that span jobs.

If a future use case demands one (e.g. a `static float3 SampleFog(float3 p)` called from multiple compute paths and from Burst), tag it `[BurstCompile]` on the method to enable IL-post-processor direct-call.

## `FunctionPointer<T>` (not currently used)

A search for `BurstCompiler.CompileFunctionPointer` and `FunctionPointer<` in `Packages/is.zori.*` returns no hits. The project does not use Burst function pointers — all polymorphism is achieved via per-job-type specialisation or runtime branching inside the kernel.

If a future kernel needs runtime-selected callbacks (e.g. SDF primitive selector with extensions outside the volumetrics package), see [`function-pointers.md`](function-pointers.md) for the canonical pattern.

## `SharedStatic<T>` (used internally only)

The project does not declare its own `SharedStatic<T>` slots in `Packages/is.zori.*`. Project usage of `SharedStatic` is only via the implicit reflection-data slots created by `IJob*Extensions.JobStruct<T>` for every Burst-compiled job (cited `UnityEngine.CoreModule.decompiled.cs:2290`).

If a future kernel needs cross-job shared mutable state (e.g. a per-frame stats counter), see [`shared-static.md`](shared-static.md).
